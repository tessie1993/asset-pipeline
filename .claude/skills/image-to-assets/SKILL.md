# Image to Godot assets

Image in, assets out: one Godot-ready `.glb` per chosen object, built from its reference image (mid
to high poly, every detail, real materials and shaders baked into textures) by a chain of builder
agents, one render cycle each: every builder compares its build with the reference itself, writes
what needs improving and hands off to the next, until nothing is left worth improving. Then the user
reviews it, it is checked in Godot and delivered in one download folder.

Nothing is fixed in advance: the objects and the look come from the image and the user's answers;
each builder finds its object's views, angles, size and triangle budget in its own reference. Run
every command from the repository root. `python3 tools/assetgen/pack.py status <pack>` shows where
each object stands and, in its `next` column, what to do next: after a context compaction or in a
new session, that is all you need to carry on.

## Rules

1. **Use the pipeline; never change it.** From step 1 to step 9 hooks lock it: only the pack's own
   folders change, git is locked, Blender builds wait for the builder's set-up and CV checks, and
   Google Flow gets only the exact Grid Architect set-ups. If a step fails because the pipeline is wrong, stop and tell
   the user the exact error.
2. **Nothing is committed during a run.** If a stop hook asks you to commit, answer that a pipeline
   run is in progress and its outputs are delivered at the end.
3. **Flow never generates on its own**: the pipeline only sets Grid Architect up (no credits);
   the user looks at each set-up and clicks Generate in Flow themselves. A hook refuses Flow's
   automatic generation during a run.
4. **Ask, don't assume**: whatever the steps do not settle goes to the user.
5. **Quality first; keep your own context small.** Builders take the time and cycles an object
   needs. You never open the builders' notes, Handoffs, job cards or images yourself unless the user
   asks why; rely on the agents' short final messages and `pack.py status`. SendUserFile shows the
   user an image without loading it into your context. Pipe long output through grep or tail.
6. **No bias.** The look comes only from the user's words. Object names, places and details say
   what the object is and its parts, materials and colours (`pack.py add` refuses look words), and
   the Flow set-up is sent exactly as `pack.py flow-call` prints it.

## 0. Tools ready

1. In a cloud session the SessionStart hook installs Blender, Godot and the CV libraries in the
   background. If `.scratch/tool-install/` exists, wait until `blender.status`, `godot.status`
   and `cv.status` are all in it (Monitor with an until-loop): `0` means installed; anything else,
   read that tool's `.log`.
2. `blender --version`, `godot --version` and `python3 tools/assetgen/cv.py --help` must work;
   otherwise run `bash tools/blender/install_blender.sh`, `bash tools/godot/install_godot.sh` or
   `bash tools/assetgen/install_cv.sh` and check again. Still failing: stop and tell the user.
3. The Agent tool must list the `asset-builder` and `asset-part-builder` types; if it does not,
   stop and tell the user.
4. Unless the run skips Flow: ToolSearch `select:mcp__google-flow__flow_connect,mcp__google-flow__flow_status,mcp__google-flow__flow_account_check,mcp__google-flow__flow_use_grid_architect,mcp__google-flow__flow_screenshot`
   must load them; if not, the Google Flow MCP server is not installed here: ask the user to run
   `bash tools/flow/install_flow_mcp.sh` on a computer whose Chrome is signed in to their Google
   account, or to go on with `skip flow` and their own images.
5. Build slots: `nproc` divided by 2 (at least 1) objects build at once (each with its lead
   builder and, inside a cycle, its part builders).

## 1. The image, the pack, the run

1. The image must be a file on disk; a pasted image's path is in the message as
   `[Image: source: <path>]`. No path: ask. Never recreate an image from memory. With `skip flow`
   the user may give several images (.png, .jpg, .jpeg, .webp), each a file on disk.
2. Pack name: the second argument, or a short snake_case name for what the image shows.
3. `python3 tools/assetgen/pack.py init <pack> <image>`, with `--skip-flow` when the user said
   `skip flow`.
4. `python3 tools/assetgen/pack.py run-start <pack>`: the run starts; the hooks snapshot and lock
   the pipeline.

## 2. Ask the user

1. Read the image (every image with `skip flow`). List every distinct object, structure, item and
   terrain piece in reading order, one line each: a number, a short name, where it is. Merge
   identical repeats and say how many. With `skip flow`, an image of one object seen from one or
   more sides is one entry.
2. AskUserQuestion, all in one call:
   - "Which of these should become 3D models?" — "All of them", "Only some (I'll type the numbers)".
   - Unless `skip flow`: "Which art style should Flow draw them in?" — "The same style as the
     image", "I'll describe it".
   - "Triangle budgets?" — "Each builder decides from the object's detail, mid to high poly
     (Recommended)", "I'll give numbers".
3. `python3 tools/assetgen/pack.py style <pack> "<style>"`: the user's words, or
   `the same art style as the reference image`.
4. Per chosen object: `python3 tools/assetgen/pack.py add <pack> <id> --name "<name>" --where
   "<where in the image>" --details "<its parts, materials and colours>" [--mount wall]
   [--budget <triangles>]`; with `skip flow` add `--reference <image(s) that show it>` (the
   source image itself when the object is in it).

## 3. Google Flow: each object from every side (not with `skip flow`)

Google Flow's Grid Architect draws one image per side of the object (front, back, left, right,
above) from the user's image. The pipeline only sets it up; the user generates.

1. `flow_connect`, then `flow_account_check`: the browser must be signed in to the user's Google
   account. `oauth_required` or a wrong account: tell the user exactly what Flow answered and wait.
2. One object at a time: `python3 tools/assetgen/pack.py flow-call <pack> <id>` prints the tool and
   its arguments; call `flow_use_grid_architect` with those arguments unchanged (a hook refuses
   anything else). It uploads the source image, fills the prompts and stops at
   `ready_for_confirmation` with a screenshot.
3. SendUserFile (`display: "render"`) with that screenshot, then AskUserQuestion: "Flow is set up to
   draw <id> from every side. Click Generate in the Flow window, then download the images." —
   "Done: here are the files" (they give the paths, one per side, front first), "Flow refused it"
   (their words), "Skip this object".
4. Done: `pack.py flow-record <pack> <id> --image <file> --image <file> ...` copies them into the
   pack as the object's references. Refused: `pack.py flow-record <pack> <id> --refused "<words>"`;
   never reword the prompts to get past a refusal; tell the user in step 8. Skip: leave it out of
   the run. Then the next object.

## 4. Builders with Handoffs, one render cycle each

1. As soon as an object has its reference (`status`: `next` is `build`) and a build slot is free,
   spawn an **asset-builder** (`subagent_type: "asset-builder"`, `run_in_background: true`) whose
   whole prompt is: `Repository: <repository root>. Pack: <pack>. Object: <id>. Build it.` The
   builder fetches its own brief with `pack.py brief`: the full first-build brief the first time,
   afterwards only the previous builder's Handoff and the paths to look at. Pass `model` only when
   the user named one.
2. Every builder does ONE render cycle: the next step, one full build, its own comparison with the
   reference and its review (what matches, what differs, what needs improving), then the Handoff for
   the next builder. Its final message starts with one of:
   - `HANDOFF <pack> <id>`: at once spawn a fresh asset-builder with the same prompt (plus any user
     wishes for this object you have not passed on yet, word for word). Never resume the old one.
   - `DONE <pack> <id>`: its own review found nothing worth improving (or the cycles are used up)
     and `pack.py done` passed: step 6 for it. There is no separate review step.
   - `BLOCKED <pack> <id>: <reason>`: tell the user and act on their answer.
3. Start the next builder whenever a slot frees. The user's feedback on a running object goes to
   its running builder with SendMessage ("Copy this into your Handoff's Standing rules") and into
   every later builder prompt for that object.

**Multitask and use the cores.** Builders run Blender in the background while they keep working,
send independent tool calls together and keep the machine's 1-minute load near `nproc` with
parallel jobs (views, part variants, a bake beside previews), not far above; no two jobs ever write
the same file. Every cycle's full build renders exactly as the kit renders (every view, lit and
clay): no reduced test renders of the full build.

## 5. Lead and part builders (inside each cycle)

You do not run this step: each builder does, and you only see its final message.

1. The builder that reads a Handoff is the cycle's **lead** (the `asset-builder`). Once, it splits
   the generator into part modules (`tools/blender/assetgen/packs/<pack>/<id>_parts/<part>.py` and
   `common.py`) and makes a test harness that rebuilds and renders one part in place.
2. For the Handoff's 2 to 4 independent part tasks it writes one job card each
   (`pack.py job-card <pack> <id> <part>`) and runs that many **part builders** at the same time
   (`subagent_type: "asset-part-builder"`). Each part builder does exactly one job, reports in a
   fixed format and ends; rework is a new job card for a new part builder. Hooks hold a part builder
   to its job card's files and to the harness: it never runs the full build.
3. The lead judges every part against the reference itself, integrates, makes the one full build,
   the full comparison, its review and the next Handoff.

The guides they follow are in `references/` next to this file: `builder_guide.md`,
`part_builder_guide.md` and `blender_tools_guide.md`. A hook hands them to every builder and part
builder when it starts.

## 6. The user reviews each object

1. SendUserFile (`display: "render"`) with `production/qa/evidence/<pack>/<id>/<id>_compare.png`
   and `<id>_turnaround.png`; in your message, the builder's short report (its final message: the
   overlap per view, the triangles and what its last review says still differs).
2. AskUserQuestion: "Are you happy with <id>?" — "Yes", "No — I'll say what to change".
3. Yes: `pack.py accept <pack> <id>`, then step 7 for it. No: `pack.py reopen <pack> <id>` and
   spawn an asset-builder with the step-4 prompt plus `The user wants: <their words>`; it continues
   from the object's Handoff with those words as a standing rule, and its DONE comes back here.

## 7. Godot check, per accepted object

`bash tools/godot/qa/check_pack_model.sh <pack> <id>` imports the model into Godot and screenshots
it from every recorded view (`<id>_godot_<view>.png`). Compare its `GODOT_MODEL` line with the
`BUILT` line: it loaded; IMPORT clean; same size (Godot's Y is Blender's Z) and triangles; every
surface has `albedo_texture`, `normal_texture` and `roughness_texture` true. Anything wrong goes
back to a builder (step 6.3) with what failed.

## 8. Export and show everything

1. Folder: the session's scratchpad directory when the system prompt names one, otherwise
   `$HOME/asset-exports`. `pack.py export <pack> <folder>` copies per object the `.glb`, its baked
   textures (`textures/`) and its renders (`renders/`: every view lit and in clay, the turnaround,
   the Godot screenshots) into `<folder>/<pack>/` and prints the path of `<folder>/<pack>.zip`.
2. In one message, per object (from `pack.py status`: triangles and size in metres, width x depth x
   height): its status, triangles, size and what its last builder's review says still differs; and
   any Flow refusals.
3. AskUserQuestion: "Which assets are good, and what should change on the others?" — "All are
   good", "Some need changes (I'll say which and what)". Changes: step 6.3 for those objects,
   then steps 6 to 8 again.

## 9. End the run

`pack.py run-end <pack>` checks that the pipeline is as it was at run-start (it restores anything
that changed), reports what was moved to `.scratch/assetgen/quarantine/`, and ends the lock.

Then `pack.py finish <pack>`: it keeps each object's `.glb`, its baked textures
(`assets/models/<pack>/<id>_textures/`) and its renders, and deletes everything else the run wrote
(the builders' notes with their reviews and Handoffs and every other .md, the generators with their
part modules and helper scripts, the job cards and test harnesses, the CV and compare images, the
build logs, the pack's scratch), so nothing of this run steers a later one. A finished pack cannot be reopened; to change an object, start a new pack.

## 10. Deliver and leave the repository clean

1. SendUserFile (`display: "attach"`) with the zip; say where the folder is.
2. AskUserQuestion: "Keep this pack's outputs in the repository?" — "No, the download is enough
   (Recommended)": `pack.py discard <pack>` removes what `finish` kept, so the repository holds
   only the pipeline again. "Yes, commit them": commit only the pack's folders
   (`design/asset-packs/<pack>/`, `assets/models/<pack>/`, `production/qa/evidence/<pack>/`) as
   `feat: <pack> asset pack`.

## Optional: one cloud machine per object (cluster)

Only when the user asks for it: each object builds on its own Claude Code cloud session, on its own
branch, while this session coordinates and runs the user's review.

1. With no run in progress here: commit the pack's inputs (`design/asset-packs/<pack>/`) on this
   session's branch (`<base>`) and push it, so every machine starts from the same pack. Run nothing
   of the pack here while the machines build.
2. Per object: `create_session` (this repository; tag `<pack>-cluster`) and send it the GO message
   below with `<pack>`, `<id>`, `<base>` and `<branch>` (`<base>-<id>`) filled in. A machine may
   ask for the user's approval in its own session before it starts a run: tell the user to approve
   there. Machines can reply with `send_message`; check on them with `get_session` and
   `list_events`, and look at their work with `git fetch origin <branch>` and
   `git show origin/<branch>:<path>`.
3. The user's feedback for an object goes to its machine with `send_message`.
4. When a machine's last commit is `feat(<id>): done (cluster)`: with no run in progress here, merge
   its branch into `<base>` (in `pack.json` keep each object's own entry from its own branch), then
   step 6 here. Changes the user wants go back to that machine as the user's words.

GO message:

```
Branch ready. Build protocol for `<id>` of pack `<pack>`:

Setup:
1. `git fetch origin <base> && git checkout -B <branch> origin/<base>`. Push only to `<branch>`. Don't open a pull request (leave one that opened by itself as a draft); the coordinator merges your branch.
2. `python3 tools/assetgen/pack.py run-start <pack>`. From here until run-end, git is locked and only the pack's folders can change. The guides and hooks are in the repository; nothing to install.

Build loop, one render cycle per builder (the image-to-assets skill, steps 4 and 5, for this one object):
- Spawn an `asset-builder` (subagent_type "asset-builder", run_in_background true) whose whole prompt is: `Repository: <repository root>. Pack: <pack>. Object: <id>. Build it.` plus the user's wishes for this object, word for word.
- Its final message starts with HANDOFF, DONE or BLOCKED:
  - HANDOFF: `python3 tools/assetgen/pack.py run-end <pack>`. Then `git add` only `production/qa/evidence/<pack>/<id>/`, `assets/models/<pack>/<id>*`, `tools/blender/assetgen/packs/<pack>/<id>.py`, `tools/blender/assetgen/packs/<pack>/<id>_parts/` (once it exists) and `design/asset-packs/<pack>/pack.json`. Commit as `wip(<id>): build <n> (cluster)` and `git push -u origin <branch>` (on a network error, retry after 2, 4, 8 and 16 s). Then run-start again and spawn the next builder with the same prompt. Keep going until DONE.
  - DONE: run-end, commit as `feat(<id>): done (cluster)`, push, and stop. Don't run pack.py accept: the coordinator shows the object to the user.
  - BLOCKED: run-end, commit and push what exists with the reason in the commit message, and stop.
- Never touch other objects' files. Never change the pipeline (tools/assetgen, .claude/, other generators). Never merge, rebase or force-push.
- The coordinator may send you the user's feedback while a builder runs: pass it to the running builder with SendMessage ("Copy this into your Handoff's Standing rules") and add it to every later builder prompt.
- If a stop hook asks you to commit during a run, answer that a pipeline run is in progress and its work is committed at the next handoff.
- Never ask for, print or move tokens or keys.
```
